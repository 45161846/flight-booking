# Проверки реализации

Проверено локально 4 ноября 2026 года на macOS ARM64, Java 17 и Podman 6.1.4.

Ниже сохранены результаты первоначальной проверки. Для HTTP-сценариев и управляемого отключения контейнеров использовались вспомогательные инструменты проверки, которые не входят в сдаваемый проект. Актуальные команды запуска, тестирования и ручной проверки отказов приведены в README; запуск системы выполняется напрямую через `podman compose up --build`.

## Автоматические тесты

Полный набор Gradle: **55 тестов, 0 ошибок, 0 пропусков**. Flight Service — 23, Booking Service — 32. Интеграционные проверки подключались к настоящим PostgreSQL 17 в отдельных базах `flights_test` и `bookings_test`.

Проверены конкурентное резервирование последнего места, одновременные повторы одного `booking_id`, однократный возврат мест, запрет позднего резерва после компенсации, rollback, цена-снимок, сохранённые операции восстановления, gRPC metadata и deadline, выбор ошибок для retry, один HALF_OPEN probe и преобразование ошибок в HTTP. Шесть тестов Flight используют настоящий сетевой Netty gRPC-сервер.

## REST на контейнерном стеке

При первоначальной автоматизированной HTTP-проверке **10 групп сценариев прошли**. Проверены все REST-методы, поиск с датой и без, валидация, отсутствие сущностей, нехватка мест, чтение после инвалидации кеша, повторная отмена.

Восемь параллельных покупателей последнего места: **1 успешное бронирование, 7 ответов HTTP 409 RESOURCE_EXHAUSTED**. Отмена победившего бронирования восстановила место. Созданные тестом бронирования отменены.

## Отказы зависимостей

При первоначальной проверке отказов **обе проверки прошли**, остановленные контейнеры восстановлены.

- После остановки `redis-master` Sentinel выбрал `redis-replica`. REST продолжил отвечать; кеш снова заполнился на новом мастере, подтверждён конечный TTL до 300 секунд.
- После остановки Flight Circuit Breaker открылся. Следующий запрос получил HTTP 503 CIRCUIT_OPEN за **0,005 секунды**. После запуска Flight запросы снова завершались HTTP 200. В логах видны CLOSED → OPEN → HALF_OPEN → CLOSED, включая возврат в OPEN после ещё неуспешной пробы.

## Границы проверки

Это локальная проверка задания: два сервиса, две PostgreSQL, Redis с репликой и тремя Sentinel работают внутри одной VM. Она не доказывает устойчивость к потере всего хоста. Совместимость с Docker Compose предусмотрена конфигурацией; фактический контейнерный запуск выполнялся через Podman. Удалённый репозиторий не создавался.

## Прямой запуск без пользовательских скриптов

После удаления пользовательских shell/Python-скриптов проверена команда `podman compose up --build -d` со стандартным провайдером podman-compose 1.6.0. Все девять контейнеров получили статус healthy, оба HTTP health endpoint вернули UP, REST вернул сведения о рейсе.

Sentinel запускается непосредственно процессом `redis-server` со статическим конфигом, без shell-entrypoint проекта. `SENTINEL ckquorum flights` подтвердил три доступных Sentinel и достижимый кворум. После остановки redis-master через `podman compose stop redis-master` чтение рейса осталось доступным, Sentinel выбрал redis-replica, а `ROLE` на нём подтвердил master. Остановленный Redis запущен обратно стандартной командой Compose. Прикладной Kotlin-код не менялся.
