# Соответствие заданию

Пункты задания проверяются последовательно: блок 5–7 оценивается после полного выполнения 1–4, блок 8–10 — после 1–7. Итоговую оценку выставляет преподаватель; эта таблица связывает требования с кодом и способом проверки.

| Пункт | Реализация | Что проверить |
| --- | --- | --- |
| 1. gRPC-контракт | [flight.proto](../flight-contract/src/main/proto/flight.proto); `protoc` и gRPC plugin в модуле `flight-contract` | Генерация при `./gradlew build`; `SearchFlights`, `GetFlight`, `ReserveSeats`, `ReleaseReservation`, `Timestamp`, enum и документированные ошибки |
| 2. ER и 3NF | [ER-диаграмма](er-diagram.md), Flyway-миграции обоих сервисов | Разделение баз, ключи, отсутствие отрицательных мест и неположительных цен, уникальность рейса по номеру и дню UTC |
| 3. PostgreSQL и оба сервиса | `flight-service`, `booking-service`, две PostgreSQL в Compose | Запуск с пустыми томами; автоматические миграции; все REST и gRPC методы |
| 4. Межсервисный gRPC | gRPC-клиент Booking; флоу создания и отмены | `GetFlight → ReserveSeats → CONFIRMED`; ошибка резерва не создаёт booking; отмена возвращает места |
| 5. Транзакционная целостность | PostgreSQL-транзакции и `SELECT FOR UPDATE` во Flight; cleanup/компенсация в Booking | Параллельное бронирование последнего места, rollback, отсутствие двойного возврата, очистка резерва после сбоя сохранения |
| 6. Аутентификация | Metadata `x-api-key`, interceptor Flight, ключ из окружения | Каждый метод с отсутствующим/неверным ключом возвращает `UNAUTHENTICATED` |
| 7. Redis Cache-Aside | Кеш рейса и поиска, TTL, hit/miss, ревизия кеша | Повторный read даёт hit; reserve/release/update меняют ревизию; свежие данные после мутации, гонки заполнения и отключения Redis |
| 8. Retry и идемпотентность | Обёртка gRPC-клиента, максимум 3 попытки; уникальный `booking_id` и блокировка команды во Flight | Повторяются только `UNAVAILABLE`/`DEADLINE_EXCEEDED`; паузы растут; один резерв при повторном и конкурентном запросе |
| 9. Redis Sentinel | Master + replica + три Sentinel; Lettuce Sentinel config | Отключить master, дождаться выбора нового; доступность приложения и повторное заполнение кеша |
| 10. Circuit Breaker | Клиентская middleware, `CLOSED/OPEN/HALF_OPEN`, параметры окружения и логи переходов | Накопить временные ошибки, увидеть быстрый 503, затем один пробный запрос и восстановление |

## Принятые решения по неполной спецификации

1. Валюта — RUB; цены хранятся целыми копейками. Суффикс `_minor` явно указывает единицу.
2. ID рейса, бронирования и резервации — UUID; `user_id` является внешним строковым идентификатором.
3. День вылета для поиска и уникальности рейса определяется в UTC. Время рейса передаётся как protobuf `Timestamp`.
4. `UpdateFlight` реализован дополнительно: он упомянут в требованиях кеширования, но отсутствует среди четырёх обязательных методов приложения.
5. Повторный `ReleaseReservation` безопасен. Для неизвестного ID он записывает запрет будущего резервирования: это требуется для компенсации задержавшихся запросов.
6. Повторное использование `booking_id` с другими параметрами отклоняется. Тот же ID нельзя заново активировать после освобождения.
7. В блоке retry «максимум 3 попытки» означает исходный вызов и не более двух повторов.
8. Для пункта 9 выбран Sentinel. Три Sentinel используются для большинства, хотя минимальный пример задания упоминает один Sentinel.
9. Данные кеша предыдущей ревизии перестают использоваться сразу после коммита мутации и физически удаляются по TTL. При ошибке Redis чтение продолжается из PostgreSQL.
10. Отдельные базы исключают общую локальную транзакцию. Сохранённая cleanup-операция обеспечивает восстановление неуспешного создания после падения процесса.
